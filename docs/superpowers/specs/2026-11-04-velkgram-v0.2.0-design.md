# Velkgram v0.2.0 — Offers, product history and new web UI

- **Date:** 2026-11-04
- **Status:** Draft, awaiting review
- **Author:** João Victor Melo (with Claude)
- **Builds on:** [v1 design](2026-11-04-velkgram-design.md). Everything there still holds unless this document changes it.

## 1. Context

v1 stores every message from the monitored channels and alerts only on wishlist matches. The stored data is invisible: there is no page to browse it, and a wish created now never sees the offers that passed before it existed. In the first real run, 186 backfilled messages were evaluated before any wish existed, and none of them could be looked at again.

v0.2.0 turns the stored messages into **offers** you can browse, gives each wish a **product page** with its price history, and redesigns the web UI in **Material Design 3 Expressive**, light and dark.

Real-time alerting stays the core. Nothing in this version may slow it down.

## 2. Goals and non-goals

### Goals
1. Browse every offer from the channels in a searchable, filterable feed.
2. Give each wish a product page: price chart, lowest price, 30-day average, last price, and every offer that matched it.
3. When a wish is created or edited, fill its history from the offers of the last 90 days.
4. Turn any feed offer into a tracked product (a pre-filled wish) with one click.
5. Keep the price history forever, while raw message text is purged after 90 days.
6. Redesign every page in M3 Expressive, responsive and mobile-first, with light and dark themes.
7. Keep the presentation decoupled, so a separate frontend repository can replace the server-rendered pages later.

### Non-goals
- **Scraping offer links** (title, image, real price, canonical product id). That is the next version (§13). v0.2.0 only keeps the links it will need.
- Automatic product grouping across wishes (clustering similar offers).
- A phone notifier (Telegram bot, WhatsApp, web push).
- A JSON API or a separate frontend repository. v0.2.0 only prepares for it (§4.4).
- Changing alert behavior: matching, pricing, dedup and latency rules stay as in v1.

## 3. Requirements

### Functional
- **FR1 — Offer per message.** Every stored message (live or backfill) becomes one offer with: channel, message id, posted date, **title**, extracted **price** (or none), **store** (or unknown), **main link**, `has_photo`, and the full text. A message with no text and no link is not an offer.
- **FR2 — Title.** The first non-empty line of the text, after stripping emoji and URLs, truncated to 140 characters on a word boundary. If that is empty, use the store name, or `"Oferta sem título"`.
- **FR3 — Price.** Same `extract_price` as alerting (v1 §6.3). One function, one behavior.
- **FR4 — Store from the link domain.** The store comes from the domain of the first link that maps to a known store (§6.3). Shorteners that belong to one store map to it (`amzn.to` → Amazon, `s.shopee.com.br` → Shopee). Generic shorteners (`bit.ly`, `tidd.ly`, `tinyurl.com`…) give **unknown**. No network call is ever made to resolve a link.
- **FR5 — Main link.** The first link that maps to a known store, else the first link, else none.
- **FR6 — Edits and deletions.** An edit updates the offer's title, price, store and text, and sets `sold_out` when the v1 sold-out hint fires. A deletion marks the offer `deleted`. The feed shows both with a chip ("esgotado", "removida") and keeps them in history.
- **FR7 — Forwards.** A forward whose origin is already an offer does not create a second feed card. The origin card shows "+N repostagens". Forwards still count as matches for wishes.
- **FR8 — Feed.**
  - Newest first, 30 cards per page, and the next page loads when the end is reached.
  - Filters: free-text search, min and max price, store (multi-select chips), "só com preço", channel.
  - Filters live in the URL query string, so a filtered feed can be bookmarked.
  - Each card shows title, price (or "preço não identificado"), store chip, channel, relative time, and the actions "Abrir" (main link) and "Acompanhar".
- **FR9 — Product page** (`/wishes/{id}`).
  - Header: wish name, terms, max price, enabled state.
  - Stats: lowest price ever, 30-day average, last price, number of matches. Each stat is empty when there is no priced match.
  - Price chart over 30 days, 90 days or all time; the default is 90 days. Each priced match is a point, and the wish's max price is a dashed line.
  - Match list, newest first, paginated like the feed. Each entry shows a chip with its source: "ao vivo" or "histórico".
- **FR10 — Live matches.** Every offer is matched against every enabled wish with the v1 rules (terms, excluded terms, max price, unknown price). Each match is stored in the wish's history, including matches that alert dedup suppressed. A match is stored once per (wish, offer).
- **FR11 — Retroactive matches.**
  - Trigger: a wish is created, or its terms or max price change.
  - Scope: offers still holding text, which means the last 90 days.
  - Effect: on edit, matches inside that window are recomputed. Matches older than the window are kept unchanged, because their text is gone. Retroactive matches never alert.
  - Status: the product page shows "buscando no histórico…" until the run finishes.
- **FR12 — "Acompanhar".** It opens the new-wish form pre-filled from the offer.
  - Name: the offer title.
  - Required terms: up to 5 significant words of the title. These are lowercased, with stopwords, prices, percentages and words under 2 characters removed, and words containing digits are kept first.
  - Max price: the offer price, if any.
  - The user edits the form and saves. Nothing is created until then.
- **FR13 — Retention.** Once a day, text older than **90 days** is purged:
  - **ingestion:** `messages.text` becomes `''`, and old `message_versions` rows are deleted;
  - **offers:** `offers.text` becomes `NULL`, and the row leaves the search index.
  - Kept forever: the offer row (title, price, store, main link, dates, flags) and every match. The feed still lists old offers, but free-text search covers only the last 90 days, and the feed says so.
- **FR14 — Rebuild.** `velkgram rebuild-offers` builds offers and matches from the messages already stored. It is idempotent and safe to run while the collector is up. It runs once after upgrading from v1.
- **FR15 — UI redesign.** Every page (login, feed, wishes and product page, channels, alerts, status) uses the new design (§8). The channel toggle shows the state as text and the action on the button ("Pausar" / "Retomar").

### Non-functional
- **NFR1 — Alert latency unchanged.** The v1 internal target (< 200 ms from handler to the first notify call) holds with the offers consumer active. The latency test runs with it subscribed.
- **NFR2 — Feed speed.** The first feed page renders in < 300 ms with 200k offers on the development machine. Search uses SQLite FTS5.
- **NFR3 — Retroactive run.** 90 days of offers (~180k) are matched for one wish in < 10 s. The run must not block the collector's event loop for more than 50 ms at a time.
- **NFR4 — No new runtime services.** Still SQLite, two processes and no build step. Python dependencies stay as in v1.
- **NFR5 — Accessibility.** WCAG AA contrast in both themes, 48 px touch targets, keyboard navigation, and every icon-only button has a label. Motion respects `prefers-reduced-motion`.

## 4. Architecture

### 4.1 New module: `offers`
It follows the v1 module layout (domain / ports / services / adapters / web / migrations) and owns the tables `offers`, `offers_fts` and `offer_matches`.

```
offers/
  domain/     title.py, stores.py, suggest.py (FR12), models.py (Offer, OfferMatch, MatchSource)
  ports/      repository.py (OfferRepository), wishes.py (WishReader), queries.py (OfferQueries)
  services/   build_offer.py (MessageReceived/Edited/Deleted → offer + live matches),
              retro_match.py (FR11), retention.py, rebuild.py (FR14)
  adapters/   sqlite/{repository.py,queries.py}, wishlist_api.py (WishReader over wishlist's public API)
  web/        router.py (feed, product page, "acompanhar"), templates/
  migrations/ 001_offers.sql
```

### 4.2 Shared deal rules
`offers` needs the same normalization, term matching and price extraction as `alerting`, and modules may not import each other's domain. These pure functions therefore move to `velkgram/shared/deals.py`: `matches_terms`, `extract_price`, and the term and wish view type they need. `alerting` imports them from there and keeps re-exporting `extract_price` in its public API. v1 rule 1 becomes: `*/domain` imports only stdlib, `shared.events`, `shared.text` and `shared.deals`. The import-linter contracts are updated to match. This is a move, not a rewrite: the existing tests move with the code, unchanged.

### 4.3 Event flow and latency
- `offers` subscribes to `MessageReceived`, `MessageEdited` and `MessageDeleted` **after** `alerting`.
- The MemoryBus awaits handlers in subscription order. So the offers handler starts with `await asyncio.sleep(0)` before touching SQLite. This lets the alert's notify task start first, which is what keeps NFR1.
- Retroactive runs are triggered on the collector by `WishlistChanged`. Wish versions are compared, so only changed wishes run.
- A run works in chunks of 2,000 offers, with `await asyncio.sleep(0)` between chunks (NFR3).
- The run state per wish (`running` / `done` + `finished_at`) is stored in a `retro_runs` table owned by `offers`, which the web reads.
- The retention job runs from the collector's housekeeping once a day, at 04:00 in `APP_TIMEZONE`. Each module purges only its own tables, through its own service: `ingestion.purge_text_before(cutoff)` and `offers.purge_text_before(cutoff)`.

### 4.4 Presentation boundary (prepares the separate frontend)
- Each page's data comes from a query service returning plain frozen dataclasses (view models), for example `FeedPage`, `OfferCard` and `ProductPage`.
- Routers only parse the request, call the service and render. Templates only format.
- No SQL and no business rule lives in a router or a template.
- When the frontend moves to its own repository, a JSON API is a new router that serializes the same view models. The services do not change.
- v0.2.0 also stops inlining any CSS or JS in templates other than the base layout. Static assets are served from `/static`.

### 4.5 Boundaries summary
- `offers` imports `shared`, plus `wishlist`'s public API from its adapter only.
- `alerting` and `ingestion` do not import `offers`.
- The `apps` wire the offers consumer, the retention job and the router.
- import-linter gets a new forbidden contract for `offers`, and the existing contracts add `offers` to their forbidden lists.

## 5. Data model (new tables, owned by `offers`)

**offers**: PK (`channel_id`, `message_id`)

| column | type | notes |
|---|---|---|
| channel_id, message_id | INTEGER | same ids as `messages` |
| posted_at | TEXT (ISO UTC) | message date |
| title | TEXT NOT NULL | FR2 |
| price_cents | INTEGER NULL | FR3 |
| store | TEXT NULL | store slug (§6.3); NULL = unknown |
| main_link | TEXT NULL | FR5 |
| has_photo | INTEGER | |
| text | TEXT NULL | NULL after retention |
| origin_channel_id, origin_message_id | INTEGER NULL | set for forwards (FR7) |
| sold_out, deleted | INTEGER | FR6 |
| updated_at | TEXT | |

Indexes: `posted_at DESC`, `(store, posted_at)`, `(origin_channel_id, origin_message_id)`.

**offers_fts**: an FTS5 external-content table over `offers(title, text)`, using the `unicode61 remove_diacritics 2` tokenizer. Triggers keep it in sync. Retention deletes the row from the index.

**offer_matches**: PK (`wish_id`, `channel_id`, `message_id`)

| column | type | notes |
|---|---|---|
| wish_id | INTEGER | wishlist id (no FK across modules) |
| channel_id, message_id | INTEGER | the offer |
| price_cents | INTEGER NULL | price at match time |
| posted_at | TEXT | copied, for chart queries without a join |
| source | TEXT | `live` or `retro` |
| matched_at | TEXT | |

Index: `(wish_id, posted_at)`.

**retro_runs**: `wish_id` PK, `wish_version`, `status` (`running` / `done` / `failed`), `started_at`, `finished_at`, `error`.

Deleting a wish deletes its `offer_matches` and `retro_runs` rows. `offers` does this when it handles `WishlistChanged`, because it owns those tables.

## 6. Domain rules

### 6.1 Title (FR2)
`title_of(text, store) -> str`. The text is normalized for display, not for matching: casing and accents are kept, emoji and URLs are removed, and whitespace is collapsed.

### 6.2 Suggested terms (FR12)
`suggest_terms(title) -> tuple[str, ...]`. It uses a pt-BR stopword list (`de, do, da, para, com, em, por, o, a, os, as, e, no, na, até, off, frete, grátis, cupom, promoção, oferta, hoje, só`). It drops prices (`R$`, numbers next to `,` decimals) and percentages, keeps the original word order, puts words with digits first, and returns up to 5 terms.

### 6.3 Stores (FR4)
`store_of(url) -> str | None`. It matches on the registrable domain and known shortener hosts. Initial table:

| slug | domains / shorteners |
|---|---|
| amazon | amazon.com.br, amzn.to, amzn.divulgador.link |
| mercadolivre | mercadolivre.com.br, mercadolivre.com, mercadolibre.com, meli.la |
| shopee | shopee.com.br, s.shopee.com.br, shope.ee |
| magalu | magazineluiza.com.br, magazinevoce.com.br, magalu.com |
| kabum | kabum.com.br |
| aliexpress | aliexpress.com, s.click.aliexpress.com, a.aliexpress.com |
| pichau | pichau.com.br |
| terabyte | terabyteshop.com.br |
| casasbahia | casasbahia.com.br |
| americanas | americanas.com.br |
| carrefour | carrefour.com.br |
| netshoes | netshoes.com.br |

Display names live in the web layer ("Amazon", "Mercado Livre"…). Adding a store is one table row plus its test.

### 6.4 Product stats (FR9)
Only priced matches count. Lowest price is over all time. The 30-day average is the mean of priced matches with `posted_at` in the last 30 days. Last price is the most recent priced match. Prices are integers in cents, and the average is rounded half-up to the cent.

## 7. Error handling
- **The offers consumer never affects alerting.** Any exception is logged with the message ids and swallowed per message. `rebuild-offers` fills the gap later.
- **A failed retroactive run** sets `retro_runs.status = failed`. The product page shows "não foi possível buscar o histórico" with a "tentar de novo" button, which triggers the run again.
- **A failed retention run** is logged and retried on the next day's run. It is idempotent.
- **A malformed link** (unparsable URL) gives store unknown, never an exception.

## 8. Web UI

### 8.1 Stack
- **Server rendering and partial updates:** FastAPI, Jinja2 and HTMX 2.0.3, all unchanged from v1. HTMX handles infinite scroll, filters, toggles and the retroactive status poll.
- **Component framework:** **Beer CSS 5.0.3**, pinned from a CDN. It provides the M3 components (buttons, cards, chips, fields, navigation bar and rail, dialogs, snackbars) and its own theme variables. The small Beer CSS JS file is allowed for its components.
- **Project stylesheet:** `velkgram/apps/web/static/velkgram.css`, with the theme tokens and the Expressive additions (§8.3). Nothing else.
- **Fonts and icons:** Roboto Flex and Material Symbols Rounded, from Google Fonts.
- **Hosting:** no build step and no `node_modules`. Every CDN URL is pinned to an exact version.

### 8.2 Theme
- **Accent:** pastel blue `#74c7ec`, which is Catppuccin's *sapphire* in Mocha.
- **Flavours:** the four [Catppuccin](https://catppuccin.com/palette) flavours are the themes. Latte is the light theme. Frappé, Macchiato and Mocha are dark. Each flavour uses its own *sapphire* as the M3 primary:

  | flavour | mode | sapphire |
  |---|---|---|
  | Latte | light | `#209fb5` |
  | Frappé | dark | `#85c1dc` |
  | Macchiato | dark | `#7dc4e4` |
  | Mocha | dark | `#74c7ec` |

- **M3 roles from the Catppuccin palette** (the same mapping for every flavour):

  | M3 role | Catppuccin colour |
  |---|---|
  | primary | sapphire |
  | secondary | lavender |
  | tertiary | mauve |
  | error | red |
  | success / price-ok | green |
  | warning ("esgotado") | peach |
  | surface, surface-dim, surface-container-lowest | base, mantle, crust |
  | surface-container-low / container / high / highest | surface0 / surface1 / surface2, with surface2 blended toward overlay0 for highest |
  | on-surface / on-surface-variant | text / subtext1 |
  | outline / outline-variant | overlay1 / overlay0 |
  | on-primary, on-secondary, on-tertiary, on-error | crust on dark flavours, base on Latte |

  Containers (`primary-container` and the rest) are the role colour mixed with the surface: 30 % on dark flavours, 20 % on Latte (CSS `color-mix(in oklab, …)`). `on-*-container` is `text`.
- **Contrast rule:** a pair that fails WCAG AA for text keeps its hue but is darkened (Latte) or lightened (dark flavours) in OKLCH until it passes. The likely case is Latte sapphire on base. Adjusted values are committed with a comment naming the original colour. A unit test checks the contrast of every on-colour/colour pair in all four flavours (NFR5).
- **Source:** the palette hex values are copied into `velkgram.css` as CSS custom properties, one block per flavour (`body.latte`, `body.frappe`, `body.macchiato`, `body.mocha`). Catppuccin is MIT-licensed, and the CSS credits it in a comment. There is no runtime dynamic colour and no generator script.
- **Theme modes:** system (default: Latte when the OS is light, Mocha when it is dark), Latte, Frappé, Macchiato and Mocha.
- **Theme picker:**
  - A menu in the top app bar lists the five modes, each with a small swatch. The choice is stored in a `theme` cookie (1 year, `SameSite=Lax`).
  - The server reads the cookie and renders the flavour class on `<body>`, plus Beer CSS `light` or `dark`. The page never flashes the wrong theme.
  - "System" renders no flavour class, and the CSS picks Latte or Mocha with `prefers-color-scheme`.

### 8.3 Expressive layer
- **Shape:** extra-large corners on cards and sheets (28 px), full-pill buttons and chips, and a corner change on press, where a button morphs from pill to rounded square.
- **Type:** Roboto Flex, with emphasized weights for headlines and prices. The price on a card uses the large emphasized title style.
- **Motion:** spring-like easing (`cubic-bezier(0.34, 1.56, 0.64, 1)`, 300–450 ms) on card entry, chip selection and navigation indicator. All of it is disabled under `prefers-reduced-motion`.
- **Color:** the primary container highlights the price and the "Acompanhar" action. The tertiary container marks retroactive ("histórico") items.

### 8.4 Layout
- **Breakpoints (M3 window classes):**
  - compact, < 600 px: bottom navigation bar, single-column cards;
  - medium, 600–839 px: navigation rail, two-column cards;
  - expanded, ≥ 840 px: navigation rail, and the feed can switch to a denser list view.
- **Navigation:** Feed (home, `/`), Desejos, Alertas, Canais, Status.
- **Hidden on compact:** the channel name on feed cards (it stays in the details), extra links, dedup details on alerts, the latency columns, and the per-channel table on Status (it becomes a summary card).
- **Price chart:**
  - A server-rendered inline SVG, with a line, points and a dashed max-price line.
  - Colors are CSS variables, so both themes work. The SVG carries a `<title>` and `<desc>`, and a visually hidden table holds the same points.
  - No chart library.

### 8.5 Pages
- **Feed (`/`):** search field and filter chips on top (a filter sheet on compact), the card grid, an infinite-scroll sentinel, and an empty state.
- **Desejos (`/wishes`):** a list of product cards with name, last price and a sparkline. A floating action button opens "Novo desejo".
- **Product (`/wishes/{id}`):** stats row, chart with a 30/90/all segmented button, match list, and edit and delete actions.
- **Alertas, Canais, Status, Login:** restyled with the same components. Channels uses the FR15 toggle.

## 9. Configuration
There are no new required variables. Optional ones:
- `RETENTION_DAYS`: default 90; minimum 30.
- `APP_TIMEZONE`: default `America/Sao_Paulo` (stdlib `zoneinfo`). It is used for the 04:00 retention run and for relative times in the UI ("hoje", "ontem"). Storage stays in UTC.

## 11. Rollout
1. `velkgram migrate` creates the `offers` tables.
2. `velkgram rebuild-offers` fills offers and matches from the existing messages.
3. Restart the collector and the web, or run `docker compose up -d --build`.
4. Bump `pyproject.toml` to `0.2.0`.

## 12. Decisions made for this spec (owner may revisit)
- **Product = wish** (hybrid option): no automatic grouping; "Acompanhar" makes any offer a product.
- **Retention: keep text for 90 days, summaries forever.**
- **UI stack:** keep server rendering (Jinja2 + HTMX) and use Beer CSS for M3 components instead of an SPA framework. No web framework ships M3 Expressive ready-made, and an SPA would add a build, Node and a JSON layer this version does not need.
- **Theme:** Catppuccin flavours mapped onto M3 roles, with sapphire (`#74c7ec` in Mocha) as primary. Latte is the light theme and Mocha the default dark one. The roles come from the palette directly instead of a generated M3 tonal palette, so the UI looks like Catppuccin, with M3 components and shapes.
- **Theme cookie instead of localStorage**, so the server renders the right theme.
- **Chart as server SVG**, with no JS chart library.
- **Rules shared with alerting move to `shared.deals`** rather than `offers` importing `alerting`.

## 13. Future direction
- **Link scraping (next version):** resolve shorteners and fetch the product page (title, image, real price, canonical id such as ASIN or MLB). This runs as a background worker, never on the alert path, with caching and per-store rate limits. It enriches `offers`, and the canonical id enables real product grouping across wishes.
- **Separate frontend repository:** a JSON API over the §4.4 view models, consumed by the new frontend.
- **Phone notifier:** a Telegram bot, WhatsApp or web push (a PWA works on this stack).
